# Consume pi-semantic-edit and pi-tree-sitter as pinned, deep-imported libraries, never as extensions

pi-tree-sitter and pi-semantic-edit are both pi extensions by packaging (each declares `pi.extensions`), and loading them as extensions would give us their tools and hooks for free — but pi-tool-ports loads them as npm dependencies instead, deep-importing only exported submodules and never invoking their index.ts entry factories. The gate logic that is private to pi-tree-sitter's index.ts (`validateContent`, `collectErrors`, `formatError`) is reimplemented byte-for-byte in the host (~100 lines) rather than reused.

Loading them as extensions was rejected: it would register their tools and event hooks (duplicate `edit`, the symbol-tool family, a second pre-write gate) alongside the host's, and their `tool_call` gate simulates edits with pi's built-in matcher — it cannot see fuzzy-only matches, which is exactly the gap this stack exists to close. The cost of the deep-import route is coupling to pinned internals (0.4.0 / 0.2.8) and reimplementing the private gate; the `node_modules`-free discovery guarantee of pi's loader is verified, so the two packages can never self-register. Re-verify deep-import targets on every dependency upgrade.
